# DP-02. 정렬 병합 조인과 해시 조인은 언제 쓰나요?

## 30초 답변

해시 조인은 한쪽 입력을 해시 테이블로 만들어 다른 쪽을 조회하므로, 입력이 정렬되지 않아도 평균적으로 선형 시간에 처리할 수 있지만 build 쪽 메모리가 필요합니다. 병합 조인은 양쪽 입력이 join key 순으로 정렬되어 있으면 두 입력을 한 번씩 훑습니다. 정렬이 안 되어 있으면 정렬 비용을 포함해야 합니다. 결과가 R행이면 두 방식 모두 결과 생성에 O(R)이 들기 때문에, 실제 전체 비용은 출력 크기도 포함해 봅니다. 그래서 입력 크기와 정렬 상태, 중복 분포, 메모리 한도, 필요한 출력 순서를 보고 실행 계획을 확인하겠습니다. 직접 만든 Python 실험에서는 이 데이터에서 해시 조인이 빨랐지만, DBMS의 실행 계획은 그 수치만으로 일반화할 수 없습니다.

## 조금 더 깊게

### 해시 조인

1. 한쪽 입력을 읽어 `key -> matching rows` 해시 테이블을 만든다(build).
2. 다른 쪽 입력을 읽으며 각 key를 찾아 일치하는 행을 내보낸다(probe).

입력이 정렬되어 있을 필요는 없습니다. 대신 build 입력을 메모리에 담을 수 있는지, 해시 충돌이나 중복 키로 결과가 얼마나 커지는지 따져야 합니다. 데이터베이스의 구현은 메모리가 부족하면 임시 저장소로 spill할 수 있고, 그 비용은 이 단순 Python 실험에 포함되지 않습니다.

### 병합 조인

두 입력을 join key 순으로 맞춘 다음, 양쪽을 앞에서부터 이동하며 일치하는 구간을 처리합니다. 입력이 이미 정렬되어 있으면 별도 해시 테이블을 만들지 않고 순차 처리할 수 있습니다. 정렬되지 않았으면 양쪽 입력을 정렬하는 시간과 메모리를 포함해야 합니다. 같은 key가 한쪽 또는 양쪽에 여러 번 있으면 일치하는 행 조합을 모두 만들어야 하므로, 입력 순회 비용 외에 결과 크기 R만큼의 출력 비용도 듭니다. 기본 입력 순회는 O(N+M), 결과 생성까지 포함하면 O(N+M+R)입니다.

조인 알고리즘은 이 둘만 있는 것이 아닙니다. 한쪽 결과가 작고 반대쪽에 적절한 인덱스가 있으면 nested-loop 계열이 나을 수도 있습니다. 실제 선택은 DBMS가 통계와 비용 추정으로 결정하므로 `EXPLAIN` 결과와 실제 실행 시간을 함께 확인합니다.

## 직접 측정한 근거

80,000행과 20,000행의 입력을 만들고 key 범위는 10,000으로 고정했습니다. 양쪽에 중복 키가 있으며, 두 조인 방식이 만든 결과 행 수와 checksum을 검증했습니다. 병합 조인은 이미 정렬된 입력과, 원본 입력을 받아 정렬까지 포함하는 경우를 따로 쟀습니다. 각 측정은 별도 Python 프로세스에서 5회 실행했습니다.

| 입력 조건 | 방법 | 시간 중앙값 (ms) | tracemalloc 최대치 (MB) |
|---|---|---:|---:|
| 이미 정렬됨 | 병합 조인 | 195.8 | 10.2 |
| 이미 정렬됨 | 해시 조인 | 57.0 | 11.3 |
| 원본 입력, 정렬 비용 포함 | 병합 조인 | 200.2 | 11.0 |
| 원본 입력 | 해시 조인 | 52.2 | 11.3 |

두 방식 모두 159,975개 결과 행과 checksum `213,040,298,565`를 냈습니다. 이 Python 구현에서는 해시 조인이 빨랐고, 병합 조인은 이미 정렬된 입력에서도 이겼다고 할 수 없었습니다. `tracemalloc`에는 공통 결과 리스트가 포함되므로 이 수치는 전체 RSS나 DB 서버 메모리가 아닙니다. 운영 DB의 알고리즘 선택을 설명하는 예시가 아니라, 정렬 상태와 자료구조에 따른 비용을 비교한 작은 실험입니다.

## 꼬리 질문

**Q. 정렬된 입력이면 병합 조인이 항상 더 빠른가요?**  
아닙니다. 정렬 상태는 정렬 단계를 생략할 수 있다는 뜻이지, 구현이나 실행 환경에서 항상 더 빠르다는 뜻은 아닙니다. 이 실험의 Python 구현에서는 이미 정렬된 입력에서도 해시 조인이 빨랐습니다. 실제 DBMS의 실행 계획과 입력 크기를 봐야 합니다.

**Q. 데이터가 메모리에 다 안 들어가면 해시 조인은 못 쓰나요?**  
DBMS에 따라 해시 테이블을 여러 배치로 나눠 임시 저장소에 spill하는 방식이 있을 수 있지만, 디스크 I/O가 늘어날 수 있습니다. 메모리 한도와 실행 계획의 실제 메모리·임시 파일 사용을 확인하겠습니다.

**Q. 결과를 join key 순으로 받아야 하면요?**  
조인 알고리즘이 결과 순서를 보장한다고 가정하면 안 됩니다. 정렬된 입력을 병합해도 최종 출력의 정렬 보장이 필요한지는 SQL `ORDER BY`로 표현하고, 추가 정렬 비용까지 확인합니다.

## 흔한 오답

- "해시 조인은 언제나 O(N+M)이고 가장 빠릅니다." → 해시 테이블의 메모리, 중복 key의 결과 수, spill, 실제 구현을 고려하지 않은 말입니다.
- "병합 조인은 무조건 정렬부터 해야 하므로 느립니다." → 입력이 이미 정렬되어 있으면 정렬 단계가 필요 없을 수 있습니다.
- "측정에서 해시 조인이 빨랐으니 DB에서도 해시 조인이 낫습니다." → 이 실험은 Python의 특정 입력·구현 결과이며, DBMS의 비용 모델과 I/O·인덱스·병렬 실행을 재현하지 않습니다.
